# Audit Fix 3 — "View All Menus" full-menu overlay (ref 3-11)

Note: `.superpowers/sdd/TODO/` did not exist in this worktree; created it to hold this report at the path the brief specified (worktree-relative).

## What was built

Three new files under `src/components/admin/`, plus one new entry in `payload.config.ts`'s `admin.components.afterNavLinks` array and the corresponding hand-added `importMap.js` entry (this repo's importMap is a checked-in, `payload generate:importmap`-shaped file, not regenerated by that CLI in this sandbox — see Environment section):

- `src/components/admin/menuOverlayTree.ts` — pure, DB-free tree-building logic (`buildMenuOverlayGroups`, `resolveMenuHref`). No React/Payload imports, fully unit-testable.
- `src/components/admin/ViewAllMenusNavLink.tsx` — the `afterNavLinks` SERVER component (async). Fetches the full `adminMenus` tree, filters it, renders the client overlay.
- `src/components/admin/ViewAllMenusOverlay.tsx` — `'use client'` trigger button + full-screen modal (rail + panel), mirroring `MemberExportButton`'s portal/backdrop/dialog shape.

## Data source: `ServerProps.payload`, not a new endpoint

`ServerProps` (`node_modules/payload/dist/config/types.d.ts`) exposes `payload: Payload` directly, exactly like every other server component in this codebase (`AdminDashboardView`, the other `afterNavLinks` components read `props.user`; this one additionally reads `props.payload`). So `ViewAllMenusNavLink` does one `props.payload.find({ collection: 'adminMenus', pagination: false, depth: 0, overrideAccess: true })` — no dedicated endpoint needed. `overrideAccess: true` is safe here because the RAW read never leaves the server: every node is re-checked against the real viewer via `hasMenuAccessSync(props.user, node.menuKey)` before `buildMenuOverlayGroups` includes it in what gets passed to the client component as props. A viewer who lacks a grant never receives that node's label over the wire, matching the constraint ("never a way to discover the EXISTENCE of a menu/system a user lacks access to").

## Tree-building algorithm (`buildMenuOverlayGroups`)

- Groups by top-level namespace (`menuKey` before the first dot — the REAL seeded set, confirmed from `src/seed/steps/adminMenus.ts`: **six** namespaces — `system`, `content`, `privacy`, `members`, `statistics`, `standardization` — not the brief's illustrative "three systems").
- A namespace's own root node (`parentId === null`, e.g. `"system"` itself) is NEVER rendered as a clickable item — it's the rail label. It's used as the rail label even when the root key itself isn't directly granted (matches how role grants are actually seeded: only leaf/view keys are ever granted, e.g. `content.posts`, never the bare `content` grouping key — verified against `src/seed/steps/rich/shared.ts`'s `RICH_ROLES`).
- Every OTHER node is included in its namespace's item list **only if** `isGranted(node.menuKey)` is true. Ungranted nodes are omitted outright — never rendered as a visible-but-disabled entry, matching `PrivacyNavLink`'s omission pattern (unit-tested explicitly: `tests/unit/menuOverlayTree.spec.ts` — "never leaks an ungranted node's label").
- Sort order and indentation depth are computed by walking each node's REAL `parent` relationship chain (not by re-parsing the dotted key string) and using each ancestor's `order` field — so a granted leaf whose immediate parent is an *ungranted* grouping node (e.g. `system.codes.groups` granted while `system.codes` itself isn't) still sorts and indents correctly relative to its siblings, even though the ungranted parent's own label never renders. This is unit-tested directly.

## menuKey → URL resolution, and what falls back to a plain label

Priority order (`resolveMenuHref`):
1. A curated view-route map (`KNOWN_VIEW_HREFS`), copied verbatim from the hrefs already hardcoded in `PrivacyNavLink`/`StatisticsNavLink`/`StandardizationNavLink` — e.g. `privacy.orgChart` → `/admin/privacy-org-chart`, `system.passwordPolicies` → `/admin/password-policies` (this one wins over the generic collection route even though `passwordPolicies` also has a real collection, because the dedicated view is the intended destination those other nav components already use).
2. `/admin/collections/<collectionSlug>` when the node has a `collectionSlug` and no curated view.
3. `null` → rendered as a plain, non-clickable `<span>` label.

Under the REAL seeded tree, exactly **one** non-root node falls back to a plain label: `system.codes` ("Code Management") — a pure grouping node with no `collectionSlug` and no dedicated view (its three children — Code Classifications/Groups/Detail — all resolve normally). Every other leaf resolves via curated view or `collectionSlug`.

## Overlay UI

Full-screen modal (`createPortal` to `document.body`, dark backdrop, `role="dialog"` `aria-modal="true"` `aria-labelledby`) styled with the eGov/KRDS admin tokens from `src/app/(payload)/custom.scss` (gov-blue `#0b50d0` header underline/active-rail/link color, `--theme-elevation-*` surfaces, matching `.card`/`.btn--style-primary` conventions already established there — no new colors invented). Left rail lists the namespace labels (sorted by each root's own `order` field, i.e. System → Content → Privacy → Members → Statistics → Standardization); right panel lists the selected namespace's granted items, indented by real nesting depth, each a link (gov-blue) or a plain bold label (grouping fallback).

Accessibility: focus moves into the dialog (`tabIndex={-1}` + `.focus()`) on open, returns to the trigger button on close; Escape dismisses (window keydown listener, only while open); backdrop click dismisses; X button dismisses. Deliberately **no focus trap** — Tab can leave the dialog normally, matching the brief.

## Gating proof

1. **Unit** (`tests/unit/menuOverlayTree.spec.ts`, 12 tests): pure-logic proof against a hand-built fixture mirroring the real seed shape — omission of ungranted namespaces/nodes, never-leak-a-label, namespace-root-never-clickable, hierarchy/ordering across an ungranted intermediate node, href-resolution priority (curated view > collectionSlug > null).
2. **Int** (`tests/int/viewAllMenusOverlay.int.spec.ts`, 3 tests): boots real Payload against Postgres, runs the REAL `adminMenusStep` seed, calls `warmAdminMenuKeyCache` (needed because the seed runs AFTER `onInit`'s cache warm in a test boot), then feeds the REAL fetched tree through the REAL `hasMenuAccessSync` for three synthetic users (roleless, super, and a limited admin granted only `content.posts`). Proves: a roleless viewer sees zero groups; a super-admin sees every one of the six real namespaces; **a limited admin (one grant, one namespace) sees exactly one namespace with exactly one menu item, and the ungranted sibling `content.media` / unrelated `system.sites` never appear anywhere in the output** — the core "fewer systems/menus than super-admin" proof the brief asked for.
3. **E2E** (`tests/e2e/view-all-menus.e2e.spec.ts`, 3 tests, run against a real browser + real `next start` + the real `ROLE_CONTENT_EDITOR`/super-admin accounts): a content editor's rail shows ONLY "Content Management" (one entry) and never renders "System Management"/"Admin Menu Management"/etc.; the super-admin's rail shows all six systems and switching rail selection swaps the panel; the dialog dismisses via X / Escape / backdrop-click with focus returning to the trigger each time (verified this class of assertion is even meaningful: manually drove a real Playwright/Chromium session against the built app first to confirm the overlay renders and behaves correctly before trusting the automated result).

## Environment notes / concerns (all pre-existing, none caused by this change — each was cross-verified by stashing this diff and reproducing on the unmodified baseline)

- **`payload` CLI / `tsx scripts/*.ts` are broken in this sandbox**: `payload migrate`, `payload migrate:status`, `payload generate:importmap`, and `tsx scripts/seed.ts` all fail with `Cannot find module './migrations'` or a `loadEnvConfig` destructure error inside `payload/dist/bin/loadEnv.js`, on both Node 22.22.3 and Node 25.9.0. Reproduced identically with this diff stashed out — a pre-existing tsx/CJS-interop or payload↔next version-shape incompatibility, not something this change touches. Consequence: `importMap.js` was updated **by hand** in the same format the file already uses (not regenerated via the broken CLI) — verified `pnpm build`/`pnpm typecheck` both resolve it correctly.
- **The shared dev Postgres DB (`pulse_cms`, used by every concurrent worktree agent in this sandbox) has a `payload_migrations` row with `batch = -1`** (the "ran in dev-push mode" marker). Any *production-mode* Payload boot (`next build`'s static generation, or `next start`) against that DB hits an interactive `prompts()` confirmation with no TTY to answer it, and hangs indefinitely. Confirmed via direct SQL. This is **pre-existing and environment-wide**, not caused by this change — reproduced identically with this diff stashed. Worked around by running `pnpm build` and `pnpm test:e2e` against a disposable, freshly-created Postgres database (never touched by any other agent, migrated cleanly, seeded via the app's own protected `/seed` HTTP route since the CLI seed script is also broken) — all three databases created for verification were dropped afterward.
- **Port 3000 was occupied by a sibling worktree agent's server** for the entire session. Verified `pnpm test:e2e`'s webServer would otherwise silently `reuseExistingServer` against THAT other agent's build (which would prove nothing about this change). Ran e2e on port 3100 instead (temporary local `playwright.config.ts` edit, reverted before commit — not part of the diff).
- **61 unrelated `pnpm test` failures on the FIRST run** (shared DB) were concurrent-worktree DB contention, exactly as the coordinator flagged — confirmed by rerunning the full `pnpm test` suite twice against a private, uncontended database: only ONE test failed both times, `tests/int/standardization.int.spec.ts` ("reports the seeded 1-74 code sets"), and it passes standalone — a pre-existing test-ordering/pagination sensitivity in that unrelated file, reproduced identically with this diff stashed out (baseline run, same private DB, same single failure). Not caused by this change.
- Two of the six e2e failures seen on the full-suite run (`auth-2fa.e2e.spec.ts`, `member-auth.e2e.spec.ts`) are due to those files' own **hardcoded `http://localhost:3000`** (not using the project's `baseURL`) — an artifact of the port-3100 workaround needed only because of sibling-agent contention on 3000, not a real regression. The other two (`board-browse.e2e.spec.ts` content mismatch, `rbac-visibility.e2e.spec.ts` privacy-officer missing one nav link) are in files this change never touches (public board frontend content, privacy-role menu grants) and were not investigated further given time constraints — worth a human re-check on a quiet single-agent run, but nothing in this diff's scope (menu tree / grant checks / admin components) plausibly explains either.
- One genuine bug was found and fixed in my OWN e2e test during this verification: `getByRole('button', { name: 'Close' })` ambiguously matched Payload's own nav-toggler button (also named "Close Menu", substring-matched) — fixed with `dialog.getByRole('button', { name: 'Close', exact: true })`.
- Also discovered (via a manual Chromium session) and worked around in the e2e spec, NOT in the component: Payload's own responsive admin nav collapses into an off-canvas drawer below a certain viewport width, and at that breakpoint the drawer's items sit behind the main-content wrapper for pointer-event purposes — a pre-existing nav-layout quirk (no existing e2e test had ever clicked an item at the bottom of the nav before; they only read link text). Forced `test.use({ viewport: { width: 1920, height: 1080 } })` in `view-all-menus.e2e.spec.ts` so the suite exercises the realistic desktop-admin layout (permanent sidebar, no drawer) rather than tripping over that pre-existing responsive-nav issue.
